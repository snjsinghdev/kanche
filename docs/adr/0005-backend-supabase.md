# Supabase: Postgres for the marble ledger, Edge Functions running the shared core

## Context and problem statement

The server owns marbles. Every ownership change is an append-only ledger event written in one transaction, and the server re-runs each shot with the same TypeScript core before any marble moves. Matches are asynchronous turns over patchy mobile data. Accounts start anonymous (no sign-up before the first shot). Furnace recipes must stay server-side.

## Decision drivers

- Real transactions and constraints for ledger invariants
- Running the identical TypeScript physics and rules on the server
- Low operations burden for one builder
- Limited lock-in

## Considered options

- **Supabase** (Postgres, Auth, Edge Functions on Deno)
- Firebase (Firestore, Auth, Cloud Functions on Node)
- A custom Node server on a VPS or Fly.io, with managed Postgres
- Nakama (game server)

## Decision outcome

Chosen option: **Supabase**.

- Postgres gives transactions, constraints, row-level security and plain SQL migrations.
- Auth supports anonymous sign-in that upgrades later.
- Edge Functions run TypeScript on Deno, which imports `packages/physics` and `packages/rules` unchanged.

Phase 0 sets up:

- `supabase/config.toml` (generated by Supabase CLI 2.120.0, `project_id = "kanche"`) and folders for `migrations/` and `tests/`
- `functions/health`, which returns `physicsVersion` and `rulesVersion`
- `functions/deno.json`, which maps `@kanche/physics` and `@kanche/rules` to the workspace sources and pins `@std/assert` 1.0.19; `deno.lock` is committed
- `deno lint`, `deno check --frozen` and `deno test --frozen` in `pnpm test`

### Consequences

- Good, because the ledger can be made correct with SQL constraints and serialisable transactions, and tested with pgTAP (Phase 6).
- Good, because one implementation of the simulation serves the client, the AI and the server. A Deno test already reproduces the Node golden hash.
- Bad, because it couples us to a vendor. Plain SQL, portable functions and no proprietary client features in the core packages keep migration possible.
- Bad, because local development of the full stack needs Docker, which this machine doesn't have. Phase 6 must provide it (or a hosted dev project) to run `supabase start` and `supabase test db`.
- **Open for Phase 6:** check that `supabase functions deploy` bundles files imported from outside `supabase/functions` (the import map points at `../../packages/...`). If it doesn't, generate a vendored copy of the core at deploy time and check it against the source by hash.

### Confirmation

`supabase/functions/health/handler.test.ts` checks the response and the cross-runtime hash. Phase 6 adds concurrency tests of the ledger invariants.

## Pros and cons of the options

### Firebase

- Good, because it's mature and has push built in.
- Bad, because there are no relational constraints, ledger invariants would live in application code, and Cloud Functions on Node would still need the core bundled separately.

### A custom Node server

- Good, because it gives full control.
- Bad, because it means running, patching, scaling and securing a server alone.

### Nakama

- Good, because it's built for games, with matchmaking and leaderboards.
- Bad, because its TypeScript runtime isn't V8 (goja), so determinism with the client isn't guaranteed. It's also another server to operate.
